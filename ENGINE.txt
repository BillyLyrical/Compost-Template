Compost::Template Runtime Engine
================================

Overview
--------

Compost::Template is a pre-compiled bytecode template engine for Perl.
Templates are compiled to a flat instruction array, cached to disk,
and interpreted at runtime. The design prioritizes three things:

  Speed    - compile once, run many; no parsing at runtime
  Safety   - sandboxed execution; no arbitrary Perl in templates
  Simplicity - minimal surface area; easy to audit and extend

The engine has two phases:

  Template Text → [Parser.pm] → Bytecode Array
                                       ↓
                                   [Cache] ← serialize to disk
                                       ↓
  Output String ← [Runtime.pm] ← Bytecode Array

These phases are completely separated. A compiled template can be
cached and reused across requests without re-parsing.


Architecture
------------

### Bytecode Format

Each instruction is a flat array: [ $debug, $op, $jump, @payload ]

  $debug   - "[file_index:line_number]" for error reporting
  $op      - opcode integer (see Constants.pm)
  $jump    - index of next instruction to execute
  @payload - op-specific data

Opcode set:

  OP_DATA       (1)  - output literal text
  OP_VAR        (2)  - resolve and output a variable
  OP_PRINTF     (3)  - sprintf-style formatted output
  OP_CALL       (4)  - call a registered Perl function
  OP_STARTBLOCK (5)  - begin a block
  OP_ENDBLOCK   (6)  - end a block
  OP_FINISH     (7)  - stop execution

Block types (payload of OP_STARTBLOCK):

  BLOCK_IF, BLOCK_NOTIF, BLOCK_ELSE, BLOCK_LOOP, BLOCK_MAP,
  BLOCK_FORMAT, BLOCK_STATE, BLOCK_RANDOM, BLOCK_DICE,
  BLOCK_INSERT, BLOCK_PREFIX

Control flow uses $jump values. Blocks use STARTBLOCK/ENDBLOCK pairs.
The block handler recursively calls _process_commands on the body.
When the body finishes, the returned jump target skips past ENDBLOCK.

### Variable Resolution

Variable paths are pre-compiled at parse time. The parser splits
"$foo.bar.baz" into ["foo", "bar", "baz"] and stores the parts
in the bytecode. At runtime, _get_var walks the parts array without
splitting or regex work.

Two namespaces:
  - pa:     current scope (changes inside loops)
  - global: reference to $self->{_PARAMS}

The -global flag forces resolution against the global namespace.
Anonymous array items use $_ which resolves to pa->{__anon__}.

### Output Model

Output is accumulated in an array and joined once at the end.
Loops reuse the output buffer by passing $s->{output} as the
5th argument to _process_commands, avoiding hash reallocation.

### Caching

Compiled templates are serialized to disk as text files with
DELIMITER ("\0\n") between entries. The cache includes:
  - Configuration (paths, flags, state)
  - Include file list (for invalidation)
  - Bytecode instructions

Cache invalidation checks modification times of all included files.
If any include has been modified, the cache is discarded and the
template is recompiled.


Design Principles
-----------------

### Compile-Time Work

The parser does the heavy lifting at compile time:
- Variable paths split into key arrays
- Syntactic sugar expanded (or-vars, interpolated strings)
- Block structure validated
- Format names checked against known formats

At runtime, the interpreter is a tight while(1) loop. Variable
lookups walk pre-compiled path arrays. There is no parsing,
no regex, no string surgery in the hot path.

### Sandboxed Execution

Templates cannot execute arbitrary Perl. They can only:
- Insert variables from the parameter hash
- Call registered functions (via set_call)
- Use predefined blocks

File paths are sanitized via safe_file(). Includes are depth-limited
(default 10). Absolute paths are blocked by default.

### Minimal Surface Area

The engine is ~600 lines of runtime code. No register files,
no complex calling conventions, no dependency injection.
Each op does one thing and returns a jump target.

This makes the engine easy to audit, extend, and debug.
The tradeoff is that advanced features require more work to add.


Completed Work
--------------

The following items from the original ENGINE.txt analysis have
been implemented:

  A. Output buffering    - array-based with final join
  B. Loop setup sharing  - _wrap_anon_item/_set_loop_vars extracted
  C. Variable paths      - pre-compiled at parse time, stored in bytecode
  D. Loop state reuse    - $output_ref avoids hash reallocation
  E. Dead code removal   - _opFinish, unused regexes, dehtmlize()
  F. Test dispatch       - single _testCompare with op parameter

Additional work:
  - Moo dependency removed (was listed but unused)
  - reply() exit code fixed (exit 1 → exit 0)
  - _doFormat passes arguments to Format.pm
  - __index__, __total__ loop variables added
  - 8 new format functions (ucfirst, lcfirst, reverse, repeat,
    center, slugify, strip_tags, truncate_words)
  - __line__, __file__ magic variables
  - Letter dice (B/X/x/A/a)


Future: Better
--------------

Developer experience and capabilities.

### Cache Versioning

Add a version header ("CTPL/2\n") to cache files. This enables:
  - Graceful invalidation on format changes
  - Forward-compatible cache loading
  - Better error messages for corrupted caches

Implementation: prepend version string, check on read, reject
mismatched versions.

### Compile-Time Validation

Extend the parser to catch more errors at compile time:
  - Unused variable warnings
  - Unreachable code after FINISH
  - Format name validation (currently runtime-only)
  - Balanced block nesting checks

### Template Inheritance

Base template defines overridable blocks:

  base.tmpl:
    <html>
    <head><% block title %>Default<% /block %></head>
    <body><% block content %><% /block %></body>
    </html>

Child template extends and overrides:

  child.tmpl:
    <% extends base.tmpl %>
    <% block title %>My Page<% /block %>
    <% block content %><p>Hello</p><% /block %>

Implementation approach:
  1. Parser: compile child, record block definitions
     (name → bytecode range)
  2. Parser: compile base, leave block bodies as placeholders
  3. Runtime: for each block in base, check if child has override.
     If so, execute child's bytecode. Otherwise, execute default.

Blocks are already isolated via STARTBLOCK/ENDBLOCK. Inheritance
is just a mechanism for selecting which block body to execute.

New opcode needed: OP_EXTENDS or BLOCK_EXTENDS block type.
Block registry stored in compiled template metadata.

### More Magic Variables

  $__time__     - current timestamp (epoch or formatted)
  $__user__     - current username (from environment)
  $__version__  - engine version

Trivial to add via the existing _get_var magic variable path.


Future: Faster
--------------

Runtime performance optimizations.

### Tighter Interpreter Loop

Current _process_commands does per-instruction:
  1. Fetch from stack
  2. Check for OP_FINISH
  3. Copy _INCLUDE_FILES and CONFIG to state
  4. Dispatch via function pointer

Optimizations:
  - Make FINISH a normal op that returns a sentinel value
  - Move _INCLUDE_FILES/CONFIG to self object (already there,
    but copied to state on every instruction)
  - Use goto &label for dispatch (Perl optimizes tail calls)

Expected improvement: 10-20% for tight loops.

### Inline Caching

For hot paths (frequent variable lookups in loops), cache
resolution results in the variable's bytecode entry. First
lookup resolves and stores; subsequent lookups return cached
value directly.

Most valuable for loops with 1000+ iterations accessing the
same variable path repeatedly.

### Constant Pool

Deduplicate strings (variable names, format names, literals)
in a shared constant pool. Instructions reference pool indices
instead of embedding strings directly.

Benefits:
  - Reduced memory usage for large templates
  - Improved cache locality
  - Faster string comparisons (integer comparison)

Format: [version, const_count, const_0, ..., instruction_0, ...]

### XS Fast Path

Compile the inner loop of _process_commands and _get_var to C/XS.
This is a last resort — pure Perl should be sufficient for most
applications. Target: 5-10x improvement for interpreter-bound
workloads.


Future: Stronger
----------------

Correctness, safety, and robustness.

### Scope Chains

Replace the two-namespace model with a scope stack:

  $var     - current scope (loop body)
  $.var    - global scope (root params)
  $..var   - parent scope (one level up)

Benefits:
  - Eliminates -global in many cases
  - Makes nested loops more intuitive
  - Clearer variable resolution rules

Implementation:
  - Store scope stack in runtime state
  - $..var walks up the stack
  - $.var goes directly to global

### Shims

Data source adapters that bring external data into scope:

  <% shim Yaml $file %> ... <% /shim %>
  <% shim CSV $file %> ... <% /shim %>

Requires:
  - Shim registry (like the call registry)
  - Parser support for shim blocks
  - Runtime that parses data and injects into scope

Potential sources: YAML, CSV, JSON, XML, DBI results.

### Assignment

Allow templates to write to a private namespace:

  <% my $foo = $val %>

Requires:
  - Writeable variable namespace in runtime state
  - New opcodes: OP_ASSIGN
  - Parser support for assignment syntax

This changes the engine's read-only model. Templates become
stateful. Consider carefully before implementing — it trades
simplicity for flexibility.


What We're NOT
--------------

  - Not Jinja2/Twig/Mason
    These are feature-rich engines with inheritance, macros,
    filters, and complex scoping. Compost is simpler by design.

  - Not a general-purpose language
    Templates are for output, not computation. Control flow
    is limited to conditionals, loops, and state matching.

  - Not a replacement for Perl
    For complex logic, use set_call(). Templates stay simple.

  - Not a streaming engine
    Output is buffered and returned as a string. The buffer
    is array-based and joined once at the end.


Notes
-----

- Parser.pm opens into package Compost::Template to share the
  namespace with Runtime.pm. Constants are shared via
  Compost::Template::Constants. This coupling is intentional —
  the parser and runtime are two halves of the same engine.

- The bytecode format is flat arrays. No schema, no
  self-describing format. A dump/undump utility would help
  with debugging and inspection.

- Includes are text-level, not structural. The included content
  is inlined into the parent template's bytecode at compile time.
  There is no include resolution at runtime.

- The state system (set_state/match) is a separate concern
  from template execution. It's used for UI state management
  and could be extracted into a standalone module.

- The engine has 85 tests covering all major features.
  Run with: perl t/Compost-Template.t

- The Todo file contains additional feature ideas: chaining
  with ;, dynamic namespaces ($x.$y.$z), relative namespaces
  ($..var), and more. These are captured in the Future sections
  above where they fit the design.
